# アーキテクチャ

## 1. 方針

MVPは「URLまたはローカルリポジトリを開く → ツリーから選ぶ → 写経する →
完了が保存される」という1本の体験を完成させます。機能別に実装を分担しますが、
途中成果を個別リリースする前提にはしません。

設計上の原則は次のとおりです。

- ドメインロジックをTUI、SQLite、ファイルシステムから独立させる。
- UIは状態を描画し、入力をアプリケーションコマンドへ変換するだけにする。
- ファイル完了やディレクトリ進捗はチャンク状態から導出する。
- 正規化済みチャンク本文のハッシュを、再走査後の進捗照合に使う。
- 外部通信はシステム`git`によるcloneだけに限定する。
- ユーザー入力をシェルへ渡さず、`git`には個別の引数として渡す。
- 端末状態は正常終了、中断、エラーのすべてで確実に復元する。

## 2. モジュール

```text
src/
  main.rs              CLI起動と終了コード
  cli.rs               引数の定義と検証
  app/                 画面遷移とユースケース
  domain/
    content.rs         正規化済み本文、チャンク、対象外理由
    typing.rs          I/O非依存の打鍵状態機械と計測
    progress.rs        進捗集計の純粋ロジック
  source/
    local.rs           ローカルパスの解決
    git.rs             clone、キャッシュ、refresh
  scan/
    walk.rs            ファイル走査と自動除外
    extract.rs         正規化と共通チャンク抽出
  store/
    sqlite.rs          スキーマ、進捗・セッション保存
  ui/
    terminal.rs        raw modeとalternate screenの生存期間
    tree.rs            ファイルツリー
    typing.rs          写経画面
    result.rs          リザルト画面
tests/
  fixtures/            小さな疑似リポジトリ
  cli.rs
  repository_flow.rs
```

実装中にファイルを細分化してよいものの、責務と依存方向は維持します。

## 3. 依存方向

```text
CLI / UI ──► App ──► Domain
               ├──► Source
               ├──► Scan
               └──► Store

Source ──► Domain
Scan   ──► Domain
Store  ──► Domain
```

`domain`は`ratatui`、`crossterm`、`rusqlite`、`git`プロセス、実ファイルI/Oに
依存しません。`ui`はSQLiteやファイル走査を直接呼びません。

## 4. 中心となる契約

実装開始時に統合担当が次の概念と公開境界を確定します。名前や詳細はRustで自然な
形へ調整できますが、責務を別モジュールへ漏らしてはいけません。

- `RepositorySource`: ローカルまたはGitキャッシュ上のルートを返す。
- `Scanner`: ルートを走査し、対象ファイル、対象外理由、チャンクを返す。
- `Chunk`: 元ファイル、表示行範囲、正規化本文、SHA-256を持つ。
- `TypingEngine`: コマンドと時刻を受け、描画可能なスナップショットを返す。
- `ProgressStore`: リポジトリ、ファイル、チャンク、セッションを保存・復元する。
- `App`: Tree、Typing、Resultの遷移とユースケースを所有する。

打鍵エンジンへの入力は、文字、Enter、Backspace、Escape、時間更新へ正規化します。
エンジンは受理位置、期待文字、ミス表示期限、完了・中断状態、計測値を返します。

## 5. データモデル

MVPでは、少なくとも次の情報を永続化します。

- repository: 同一性、表示名、入力元、キャッシュパス、最終利用日時
- repo_file: repositoryとの関係、相対パス、自動対象外理由
- chunk: fileとの関係、正規化本文ハッシュ、表示行範囲、現在有効か
- chunk_progress: 完了状態と完了日時
- session: chunk、開始・終了、完了/中断、入力数、ミス数

ファイルやリポジトリの完了率は保存せず、チャンクから集計します。スキーマの列名と
マイグレーション方式は実装時に決定し、`docs/decisions.md`へ記録します。

## 6. 主要フロー

### 起動

1. CLIがURLまたはローカルパスを検証する。
2. Sourceが利用可能なローカルルートを返す。
3. Scannerが対象判定とチャンク抽出を行う。
4. Storeがハッシュで既存進捗を対応付ける。
5. AppがTree状態を構築し、UIを開始する。

### チャンク完走

1. UIが端末イベントを打鍵コマンドへ変換する。
2. TypingEngineが入力を判定し、状態を更新する。
3. 完走時にAppがセッションとチャンク完了を1トランザクションで保存する。
4. Appが集計し直してResultを表示する。
5. Treeへ戻ると更新済み進捗が表示される。

### 中断

Escapeでは中断セッションだけを記録し、チャンク完了を更新しません。次回はチャンク
先頭から開始します。

## 7. エラーと安全性

- ユーザーが修正できる入力・設定・gitエラーには、原因と次の行動を表示する。
- 内部エラーでもpanicを通常の制御フローに使わない。
- cloneはアプリ管理下の確定したキャッシュパスだけへ行う。
- リポジトリ走査ではシンボリックリンクを既定で辿らない。
- `--purge`は削除対象を表示して確認を取り、管理ディレクトリ外を削除しない。
- 生の打鍵列は永続化せず、統計に必要な集計値だけを保存する。
- DB更新はトランザクションで行い、完了状態とセッションを食い違わせない。
- raw modeとalternate screenはRAIIガードで管理する。

## 8. 将来拡張

tree-sitterによるラベル、dependencyモード、統計、演出は既存境界の実装追加として
導入します。MVPの打鍵エンジン、チャンクID、進捗集計を作り直さずに拡張できる
ことを設計上の目標とします。
